# Оперативно ръководство (RUNBOOK.md)

Този наръчник дефинира стандартите за поддръжка, процедурите при инциденти, архивирането и плана за аварийно възстановяване на **Saza Event Portal** съгласно Раздели 22.3, 22.4 и 23 от Спецификацията.

---

## 🎯 Оперативни цели за непрекъсваемост (SLA / DR)

- **RPO (Recovery Point Objective)**: **до 24 часа** (максимално приемлива загуба на данни от последен архив).
- **RTO (Recovery Time Objective)**: **до 8 часа** (максимално време за пълно възстановяване на функционалността в изолирана или нова продукционна среда).

## 💾 Резервни копия (Backup & Archival)

### Важно техническо разграничение
> [!IMPORTANT]
> Резервното копие на PostgreSQL / Supabase базата данни съдържа **единствено метаданните за файловете** (`storage.objects`, `documents`, `document_versions`), но **НЕ съдържа самите двоични файлови обекти (BLOBs)**.
> Пълното резервно копие изисква две отделни процедури: архив на базата и синхронизация на файловото хранилище.

### 1. Ежедневен архив на базата данни
```bash
# Автоматичен pg_dump през Supabase CLI или PostgreSQL клиент
pg_dump --clean --if-exists --no-owner --no-privileges \
  -h db.sazaevents.com -U postgres -d postgres \
  -F c -b -v -f "/backups/db/db_backup_$(date +%Y%m%d_%H%M%S).dump"
```

### 2. Ежедневен архив на частните файлове (Storage Bucket)
```bash
# Синхронизация на S3-съвместимия bucket към студен архивен сторидж
aws s3 sync s3://saza-event-documents-prod \
  s3://saza-event-backups-cold/documents/$(date +%Y%m%d)/ \
  --storage-class GLACIER_IR
```

## 🔄 Процедура за пълно възстановяване (Disaster Recovery Restore)

Преди продукционно пускане трябва да бъде извършено поне едно пробно възстановяване в изолирана тестова среда (Staging).

### Стъпка 1: Възстановяване на схемата и данните
```bash
pg_restore -h staging-db.sazaevents.com -U postgres -d postgres \
  --clean --if-exists --no-owner "/backups/db/db_backup_LATEST.dump"
```

### Стъпка 2: КРИТИЧНО — Замразяване на чакащите съобщения в Outbox
> [!WARNING]
> Веднага след възстановяване на база от по-стар архив, старата опашка за известия може да съдържа записи със статус `pending`.
> Ако worker-ът се стартира преди тази стъпка, клиентите ще получат дублирани или остарели имейли и покани!

Изпълнете незабавно след restore:
```sql
-- Отмяна на всички висящи съобщения, генерирани преди възстановяването
UPDATE notification_outbox
SET status = 'cancelled',
    error_details = 'Cancelled automatically following disaster recovery database restore.'
WHERE status IN ('pending', 'processing');
```

### Стъпка 3: Синхронизиране на файловите обекти
```bash
aws s3 sync s3://saza-event-backups-cold/documents/LATEST/ s3://saza-event-documents-staging
```

### Стъпка 4: Верификация на работоспособността (Smoke Test)
1. Влезте с акаунт на координатор и потвърдете достъп до списъка със събития.
2. Влезте като Клиент А и отворете клиентския обзор.
3. Изтеглете произволен файл от раздел „Документи“ за проверка на валидността на ключовете.
4. Проверете последното одобрено решение и салдото по бюджета.

## 🚨 Процедури при оперативни инциденти (Incident Runbooks)

### Инцидент 1: Спрял или отказващ пощенски доставчик (Email Failure)
- **Симптоми**: Записите в `notification_outbox` остават със статус `pending` или нараства броят на опитите (`attempts > 1`).
- **Отговорник**: Дежурен системен инженер / Бекенд програмист.
- **Действия**:
  1. Проверете статуса на доставчика (напр. status.resend.com или status.sendgrid.com).
  2. Проверете в логовете за грешка от тип `401 Unauthorized` (изтекъл ключ) или `429 Too Many Requests` (превишен лимит).
  3. Благодарение на **Transactional Outbox модела**, клиентските транзакции в портала **не са загубени** и функционират нормално.
  4. При нужда променете доставчика в `.env` (`MAIL_PROVIDER_KEY`) и рестартирайте процеса на worker-а.
  5. Записите с неуспех ще бъдат автоматично изпратени отново според експоненциалния backoff.

---

### Инцидент 2: Забавен или блокиран Outbox Worker
- **Симптоми**: Сигнал за най-стар чакащ запис в outbox над 15 минути.
- **Действия**:
  1. Изпълнете заявка за отключване на "зависнали" лийзове (ако процесът е прекратен аварийно):
     ```sql
     UPDATE notification_outbox
     SET locked_until = NULL, status = 'pending'
     WHERE status = 'processing' AND locked_until < NOW();
     ```
  2. Рестартирайте фоновия worker:
     ```bash
     npm run worker:restart
     ```
  3. Следете за спадане на опашката към 0.

---

### Инцидент 3: Компрометиран акаунт на служител
- **Симптоми**: Подозрителна активност в одитния лог или сигнал от служител за откраднато устройство/парола.
- **Отговорник**: Owner / Администратор на организацията.
- **Действия**:
  1. **Мигновено прекратяване на членството** през базата данни или административния екран:
     ```sql
     DELETE FROM memberships 
     WHERE user_id = 'COMPROMISED_USER_ID' AND organization_id = 'ORG_ID';
     ```
  2. Всички активни сесии на този потребител ще бъдат отхвърлени на **следващата им заявка** с `403 Forbidden` (гарантирано от теста `T07`).
  3. Деактивирайте потребителя в Supabase Auth:
     ```sql
     UPDATE auth.users SET banned_until = '2099-01-01' WHERE id = 'COMPROMISED_USER_ID';
     ```
  4. Прегледайте одитния лог (`audit_log`) за действия, извършени от този акаунт през последните 24 часа.

---

### Инцидент 4: Грешно публикуван етап или вътрешна чернова
- **Симптоми**: Координатор по грешка е публикувал незавършен етап или поверителна информация.
- **Действия**:
  1. Координаторът или мениджърът незабавно отменя публикацията:
     ```sql
     UPDATE milestones 
     SET is_published = false, published_at = NULL 
     WHERE id = 'MILESTONE_ID';
     ```
  2. Проверете дали има чакащо известие в outbox за тази публикация:
     ```sql
     UPDATE notification_outbox 
     SET status = 'cancelled' 
     WHERE payload->>'milestone_id' = 'MILESTONE_ID' AND status = 'pending';
     ```
  3. При въпрос от клиент, изпратете уточняващо съобщение в секцията „Разговори“.

---

### Инцидент 5: Изтекъл системен ключ или сертификат
- **Действия**:
  1. Генерирайте нов ключ през конзолата на доставчика (Supabase / Storage / Mail).
  2. Актуализирайте секретите в средата (Vercel / Railway / AWS Parameter Store).
  3. Извършете плавен рестарт (Zero-Downtime Rolling Restart) на контейнерите.
  4. Проверете логовете за изчезване на `401/403` грешки.

## 📈 Наблюдение и метрики (Monitoring Alerts)

Наблюдават се следните прагове:
- `Outbox Queue Age > 10m`: Сигнал към дежурния екип за изоставане на известията.
- `Failed Logins > 5 per minute per IP`: Автоматично временно блокиране по IP за защита от brute force.
- `Storage Used > 85%`: Сигнал за разширяване на капацитета.
- `Database CPU > 80% за > 5m`: Проверка за тежки бавни заявки в `pg_stat_statements`.
